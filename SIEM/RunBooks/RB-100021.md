# Runbook — Multiple Suricata Stream 3-Way Handshake SYN-ACK Resends with Divergent ACK

## 1. Metadata & Overview

**Purpose:** Investigate high-frequency TCP stream anomalies during initial session establishment where retransmitted SYN-ACK packets contain conflicting acknowledgment numbers from a single source IP.

**Scenario:** Stateless TCP handshake manipulation, embryonic connection pool exhaustion (SYN flood), or packet fuzzing targeting pre-established network sockets.

**Environment:** SOC Lab / Ubuntu Endpoint / Suricata NIDS / Wazuh SIEM

---

## 2. Trigger & Alert Information

**Wazuh Rule:** `100021`

**Level:** `8`

**Description:** Multiple SURICATA STREAM 3way handshake SYNACK resend with different ack from SAME IP.

**Parent Rule:** `100019` (Base Level 1 rule matching Suricata SID `2210004`)

**Detection Pattern:** 10 or more `2210004` events from the same `src_ip` within 10 seconds (`ignore="30"` active).

**MITRE ATT&CK:** `T1498.001 — Direct Network Flood` (and `T1498 — Network Denial of Service`)

**Tactic:** `Impact`

**Groups:** `suricata`, `soc_lab_scan`, `dos`

---

## 3. Collect Information

Record the following from the Wazuh alert and raw telemetry:

* Alert Timestamp & Incident ID
* Attacker Source IP (`data.src_ip`)
* Attacker Source Port (`data.src_port`)
* Target Destination IP (`data.dest_ip`)
* Target Destination Port (`data.dest_port`)
* Protocol (`TCP`) & Header Flags (`SYN-ACK`)
* Agent Name / ID (`agent.name`, `agent.id`)
* Active Response execution logs (`firewall-drop` on endpoint)
* Target socket state (`netstat -nat | grep -c SYN_RECV` or `ss -tan state syn-recv`)

---

## 4. Investigate

Check:

1. **Handshake Integrity:** Are ACK numbers diverging during the initial 3-way negotiation phase, indicating synthetic packet generation (`hping3`, `scapy`) rather than an RFC-compliant TCP stack?
2. **Backlog Saturation:** Is the embryonic connection pool filling up on the target endpoint (risk of dropped legitimate incoming handshakes)?
3. **Target Impact:** Did destination listening services drop incoming connections, experience elevated latency, or crash during the packet burst?
4. **Correlated Security Events:**
* Did the source IP trigger concurrent UFW block rules (`100010`, `100011`)?
* Did Suricata trigger related stream rules (e.g., `2210008`, `2210023`) or SYN flood detection (`1000002` / `86601`)?


5. **Source Classification:** Is the source IP a known internal penetration testing node (e.g., Kali Linux lab VM) executing a flood test, or an unauthorized external IP?
6. **Automated Containment Validation:** Verify whether Wazuh Active Response successfully executed `firewall-drop` on the endpoint for the offending source IP.

---

## 5. Decide

### Authorized Testing / Simulation

* Confirm the handshake flood was initiated by an authorized analyst or scheduled lab simulation.
* Verify detection rules and automated Active Response fired accurately.
* Document findings and close as **Authorized Activity**.

### Confirmed Malicious / Hostile Flood

* Confirm sustained abnormal 3-way handshake manipulation targeting endpoint services.
* Validate that automated Active Response dropped the IP, or escalate if packets continue to bypass.
* Close as **True Positive — Denial of Service Attempt / Handshake State Manipulation**.

### False Positive / Multi-Path Routing

* Check for asymmetrical routing or load balancers with active SYN proxy mechanisms duplicating and re-tagging handshake packets.
* Adjust rule thresholds if legitimate proxy infrastructure consistently triggers the 10-event window.

---

## 6. Automated Containment Verification

* Check Wazuh Manager active response logs:
* Look for `active-response/bin/firewall-drop` execution against `<SRC_IP>`.


* Verify endpoint firewall state:
* Run `sudo ufw status numbered` or `sudo iptables -L -n -v` to ensure the drop rule is actively matching.


* Confirm TCP state table clearance:
* Verify half-open connections have cleared and listener backlog is healthy (`ss -tan state syn-recv`).



---

## 7. Documentation & Review

* Log incident details, attack timeline, total suppressed volume, and impact metrics.
* Review if the 30-second cooldown (`ignore="30"`) adequately protected the SIEM queue during the attack window.

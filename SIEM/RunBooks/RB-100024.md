# Runbook — Multiple Suricata Stream 3-Way Handshake SYN Resends with Conflicting Sequence Numbers

## 1. Metadata & Overview

**Purpose:** Investigate high-frequency TCP handshake anomalies where repeated initial SYN packets carry conflicting sequence numbers while the endpoint socket is in a `SYN_RECV` state.

**Scenario:** High-rate TCP SYN flood, Initial Sequence Number (ISN) randomization, or raw-socket DoS attack attempting to saturate the embryonic connection queue.

**Environment:** SOC Lab / Ubuntu Endpoint / Suricata NIDS / Wazuh SIEM

---

## 2. Trigger & Alert Information

**Wazuh Rule:** `100024`

**Level:** `8`

**Description:** Multiple SURICATA STREAM 3way handshake SYN resend different seq on SYN recv from SAME IP.

**Parent Rule:** `100022` (Base Level 1 rule matching Suricata SID `2210008`)

**Detection Pattern:** 10 or more `2210008` events from the same `src_ip` within 10 seconds (`ignore="30"` active).

**MITRE ATT&CK:** `T1498.001 — Direct Network Flood` (and `T1498 — Network Denial of Service`)

**Tactic:** `Impact`

**Groups:** `suricata`, `soc_lab_scan`, `dos`

---

## 3. Collect Information

Record the following from the Wazuh alert and raw telemetry:

* Alert Timestamp & Incident ID
* Attacker Source IP (`data.src_ip`)
* Attacker Source Port (`data.src_port`)
* Target Destination IP (`data.dest_ip`)
* Target Destination Port (`data.dest_port`)
* Protocol (`TCP`) & Header Flags (`SYN`)
* Agent Name / ID (`agent.name`, `agent.id`)
* Active Response execution logs (`firewall-drop` on endpoint)
* Target socket state (`netstat -nat | grep -c SYN_RECV` or `ss -tan state syn-recv`)

---

## 4. Investigate

Check:

1. **Sequence Number Manipulation:** Standard TCP stacks retransmit identical sequence numbers when handshakes time out. Are sequence numbers randomized per packet (classic signature of `hping3 --flood -S` or raw packet injectors)?
2. **Backlog & Listener Saturation:** Is the half-open connection pool filling up on the target endpoint, risking dropped legitimate incoming connections?
3. **Target Impact:** Did destination listening services drop connections, experience elevated latency, or crash during the burst?
4. **Correlated Security Events:**
* Did the source IP trigger concurrent UFW block rules (`100010`, `100011`)?
* Did Suricata trigger related stream rules (e.g., `2210004`, `2210027`) or dedicated SYN flood detection (`1000002` / `86601`)?


5. **Source Classification:** Is the source IP a known internal penetration testing node (e.g., Kali Linux lab VM) conducting flood tests, or an unauthorized external actor?
6. **Automated Containment Validation:** Verify whether Wazuh Active Response successfully executed `firewall-drop` on the endpoint for the offending source IP.

---

## 5. Decide

### Authorized Testing / Simulation

* Confirm the SYN flood was initiated by an authorized analyst or scheduled lab simulation.
* Verify detection rules and automated Active Response fired accurately.
* Document findings and close as **Authorized Activity**.

### Confirmed Malicious / Hostile Flood

* Confirm sustained abnormal 3-way handshake manipulation targeting endpoint services.
* Validate that automated Active Response dropped the IP, or escalate if packets continue to bypass.
* Close as **True Positive — Denial of Service Attempt / TCP SYN Flood**.

### False Positive / Severe Network Retransmissions

* Check for extreme packet duplication or faulty middlebox hardware re-injecting distorted frames.
* Adjust rule thresholds if legitimate multi-path network devices regularly breach the 10-event threshold.

---

## 6. Automated Containment Verification

* Check Wazuh Manager active response logs:
* Look for `active-response/bin/firewall-drop` execution against `<SRC_IP>`.


* Verify endpoint firewall state:
* Run `sudo ufw status numbered` or `sudo iptables -L -n -v` to ensure the drop rule is actively matching.


* Confirm TCP state table clearance:
* Verify half-open connections have cleared and listener backlog is healthy (`ss -tan state syn-recv`).



---

## 7. Documentation & Review

* Log incident details, attack timeline, total suppressed volume, and impact metrics.
* Review if the 30-second cooldown (`ignore="30"`) adequately protected the SIEM queue during the attack window.

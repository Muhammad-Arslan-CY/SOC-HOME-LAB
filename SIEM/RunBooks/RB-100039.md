# Runbook — Multiple Suricata Stream Established SYN Resends with Conflicting Sequence Numbers (Secondary SID)

## 1. Metadata & Overview

**Purpose:** Investigate high-frequency TCP stream anomalies where `SYN` packets with conflicting sequence numbers target active, established connections from a single source IP.

**Scenario:** Session hijacking, blind in-session TCP reset attacks, or stateless flood utilities injecting `SYN` packets into active sessions to disrupt data streams.

**Environment:** SOC Lab / Ubuntu Endpoint / Suricata NIDS / Wazuh SIEM

---

## 2. Trigger & Alert Information

**Wazuh Rule:** `100039`

**Level:** `8`

**Description:** Multiple SURICATA STREAM ESTABLISHED SYN resend with different seq from SAME IP.

**Parent Rule:** `100037` (Base Level 1 rule matching Suricata SID `2210024`)

**Detection Pattern:** 10 or more `2210024` events from the same `src_ip` within 10 seconds (`ignore="30"` active).

**MITRE ATT&CK:** `T1498.001 — Direct Network Flood` (and `T1498 — Network Denial of Service`)

**Tactic:** `Impact`

**Groups:** `suricata`, `soc_lab_scan`, `dos`

---

## 3. Collect Information

Record the following from the Wazuh alert and raw telemetry:

* Alert Timestamp & Incident ID
* Attacker Source IP (`data.src_ip`)
* Attacker Source Port (`data.src_port`)
* Target Destination IP (`data.dest_ip`)
* Target Destination Port (`data.dest_port`)
* Protocol (`TCP`) & Header Flags (`SYN`)
* Agent Name / ID (`agent.name`, `agent.id`)
* Active Response execution logs (`firewall-drop` on endpoint)
* Target socket state (`ss -tan state established`)

---

## 4. Investigate

Check:

1. **In-Session Packet Injection:** Are `SYN` packets arriving on established connections with forged or out-of-order sequence numbers (RFC 793 violation)?
2. **Session Disruption Scope:** Did active long-lived connections (e.g., SSH, database sync, persistent HTTP) experience unexpected resets or connection drops?
3. **Traffic Pattern:** Is the source IP flooding a single active socket or scanning multiple established ports simultaneously?
4. **Correlated Security Events:**
* Did the source IP trigger concurrent UFW block rules (`100010`, `100011`)?
* Did Suricata trigger related stream rules (e.g., `2210027`, `2210008`, `2210023`) or custom DoS rules (`1000002` / `86601`)?


5. **Source Classification:** Is the source IP a known internal penetration testing node (e.g., Kali Linux lab VM) conducting flood tests, or an unauthorized external actor?
6. **Automated Containment Validation:** Verify whether Wazuh Active Response successfully executed `firewall-drop` on the endpoint for the offending source IP.

---

## 5. Decide

### Authorized Testing / Simulation

* Confirm the scan/flood was initiated by an authorized analyst or scheduled lab exercise.
* Verify detection rules and automated Active Response fired accurately.
* Document findings and close as **Authorized Activity**.

### Confirmed Malicious / Session Reset Flood

* Confirm sustained transmission of in-session `SYN` packets targeting established connections.
* Validate that automated Active Response dropped the IP, or escalate if packets continue to bypass.
* Close as **True Positive — Denial of Service Attempt / In-Session TCP Injection**.

### False Positive / Asymmetric Connection State

* Check for middlebox state table loss or asymmetric network paths causing retransmission mismatches.
* Adjust rule thresholds if legitimate multi-path network devices regularly breach the 10-event threshold.

---

## 6. Automated Containment Verification

* Check Wazuh Manager active response logs:
* Look for `active-response/bin/firewall-drop` execution against `<SRC_IP>`.


* Verify endpoint firewall state:
* Run `sudo ufw status numbered` or `sudo iptables -L -n -v` to ensure the drop rule is actively matching.


* Confirm TCP state table clearance:
* Verify stale sockets have dropped and listener backlog is healthy (`ss -tan state established`).



---

## 7. Documentation & Review

* Log incident details, attack timeline, total suppressed volume, and impact metrics.
* Review if the 30-second cooldown (`ignore="30"`) adequately shielded the SIEM from queue congestion during the attack window.

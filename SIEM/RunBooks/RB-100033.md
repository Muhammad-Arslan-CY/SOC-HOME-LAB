# Runbook — Multiple Suricata Stream Established Invalid ACK from Same Source

## 1. Metadata & Overview

**Purpose:** Investigate high-frequency TCP stream anomalies where invalid acknowledgment numbers are received for connections tracked in an `ESTABLISHED` state from a single source IP.

**Scenario:** In-session TCP desynchronization, blind data/ACK injection, session disruption attacks, or stateless high-rate ACK floods hitting active sockets.

**Environment:** SOC Lab / Ubuntu Endpoint / Suricata NIDS / Wazuh SIEM

---

## 2. Trigger & Alert Information

**Wazuh Rule:** `100033`

**Level:** `8`

**Description:** Multiple SURICATA STREAM ESTABLISHED invalid ack from SAME IP.

**Parent Rule:** `100031` (Base Level 1 rule matching Suricata SID `2210029`)

**Detection Pattern:** 10 or more `2210029` events from the same `src_ip` within 10 seconds (`ignore="30"` active).

**MITRE ATT&CK:** `T1498.001 — Direct Network Flood` (and `T1498 — Network Denial of Service`)

**Tactic:** `Impact`

**Groups:** `suricata`, `soc_lab_scan`, `dos`

---

## 3. Collect Information

Record the following from the Wazuh alert and raw telemetry:

* Alert Timestamp & Incident ID
* Attacker Source IP (`data.src_ip`)
* Attacker Source Port (`data.src_port`)
* Target Destination IP (`data.dest_ip`)
* Target Destination Port (`data.dest_port`)
* Protocol (`TCP`) & Header Flags (`ACK`)
* Agent Name / ID (`agent.name`, `agent.id`)
* Active Response execution logs (`firewall-drop` on endpoint)
* Target socket state (`ss -tan state established`)

---

## 4. Investigate

Check:

1. **In-Session ACK Validity:** Is the acknowledgment number outside the expected window for an already established TCP session, indicating an attempt to desynchronize the stream or trigger TCP resets?
2. **Session Disruption Scope:** Did active application sessions (e.g., SSH, HTTP/S, database connections) experience sudden disconnections, stalled transfers, or payload drops during the burst?
3. **Traffic Pattern:** Is the source IP sending crafted ACK packets with static or pseudo-random ACK values against established server listening ports?
4. **Correlated Security Events:**
* Did the source IP trigger concurrent UFW block rules (`100010`, `100011`)?
* Did Suricata trigger related stream rules (e.g., `2210045`, `2210027`, `2210023`) or custom DoS rules (`1000002` / `86601`)?


5. **Source Classification:** Is the source IP an internal testing machine (e.g., Kali Linux lab VM) running flood scripts, or an unauthorized external actor?
6. **Automated Containment Validation:** Verify whether Wazuh Active Response successfully executed `firewall-drop` on the endpoint for the offending source IP.

---

## 5. Decide

### Authorized Testing / Simulation

* Confirm the scan/flood was initiated by an authorized analyst or scheduled lab simulation.
* Verify detection rules and automated Active Response fired accurately.
* Document findings and close as **Authorized Activity**.

### Confirmed Malicious / Session Injection Attempt

* Confirm sustained transmission of invalid ACK packets targeting active connection states.
* Validate that automated Active Response dropped the IP, or escalate if traffic continues to bypass.
* Close as **True Positive — Denial of Service Attempt / In-Session ACK Manipulation**.

### False Positive / Asymmetrical WAN Acceleration

* Check if intermediate WAN optimizers, TCP proxies, or load balancers performed out-of-order sequence aggregation that confused the Suricata state tracker.
* Adjust rule thresholds if legitimate multi-path network devices regularly breach the 10-event threshold.

---

## 6. Automated Containment Verification

* Check Wazuh Manager active response logs:
* Look for `active-response/bin/firewall-drop` execution against `<SRC_IP>`.


* Verify endpoint firewall state:
* Run `sudo ufw status numbered` or `sudo iptables -L -n -v` to ensure the drop rule is actively matching.


* Confirm TCP state table clearance:
* Verify stale sockets have dropped and listener backlog is healthy (`ss -tan state established`).



---

## 7. Documentation & Review

* Log incident details, attack timeline, total suppressed volume, and impact metrics.
* Review if the 30-second cooldown (`ignore="30"`) adequately protected the SIEM queue during the attack window.

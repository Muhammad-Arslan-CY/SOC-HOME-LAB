# Runbook — Multiple Suricata Stream 3-Way Handshake Wrong Sequence & Wrong ACK from Same Source

## 1. Metadata & Overview

**Purpose:** Investigate high-frequency TCP stream anomalies where handshake packets contain invalid/conflicting sequence and acknowledgment numbers simultaneously from a single source IP.

**Scenario:** Stateless TCP fuzzing, aggressive handshake corruption attacks, raw packet crafting (`hping3`, `scapy`), or malformed DoS flooding attempting to exhaust connection tables or crash network stack parsers.

**Environment:** SOC Lab / Ubuntu Endpoint / Suricata NIDS / Wazuh SIEM

---

## 2. Trigger & Alert Information

**Wazuh Rule:** `100036`

**Level:** `8`

**Description:** Multiple SURICATA STREAM 3way handshake wrong seq wrong ack from SAME IP.

**Parent Rule:** `100034` (Base Level 1 rule matching Suricata SID `2210010`)

**Detection Pattern:** 10 or more `2210010` events from the same `src_ip` within 10 seconds (`ignore="30"` active).

**MITRE ATT&CK:** `T1498.001 — Direct Network Flood` (and `T1498 — Network Denial of Service`)

**Tactic:** `Impact`

**Groups:** `suricata`, `soc_lab_scan`, `dos`

---

## 3. Collect Information

Record the following from the Wazuh alert and raw telemetry:

* Alert Timestamp & Incident ID
* Attacker Source IP (`data.src_ip`)
* Attacker Source Port (`data.src_port`)
* Target Destination IP (`data.dest_ip`)
* Target Destination Port (`data.dest_port`)
* Protocol (`TCP`) & Header Flags
* Agent Name / ID (`agent.name`, `agent.id`)
* Active Response execution logs (`firewall-drop` on endpoint)
* Target socket and system health (`netstat -nat | grep -c SYN_RECV` or `ss -tan state syn-recv`)

---

## 4. Investigate

Check:

1. **RFC 793 Protocol Violation:** Dual invalidation of both Sequence and ACK fields indicates synthetic or malformed packet generation. Are sequence and ACK numbers completely pseudo-randomized?
2. **Handshake Disruption Scope:** Is the attack targeting a single listening daemon (e.g., Web, SSH) to exhaust embryonic connection state memory, or randomly scanning ports?
3. **Target Impact:** Did destination listening services drop incoming connections, experience packet drops, or crash during the burst?
4. **Correlated Security Events:**
* Did the source IP trigger concurrent UFW block rules (`100010`, `100011`)?
* Did Suricata trigger related stream rules (e.g., `2210008`, `2210004`, `2210023`) or SYN flood detection (`1000002` / `86601`)?


5. **Source Classification:** Is the source IP an internal testing machine (e.g., Kali Linux lab VM) conducting flood tests, or an unauthorized external IP?
6. **Automated Containment Validation:** Verify whether Wazuh Active Response successfully executed `firewall-drop` on the endpoint for the offending source IP.

---

## 5. Decide

### Authorized Testing / Simulation

* Confirm the scan/flood was initiated by an authorized analyst or scheduled lab simulation.
* Verify detection rules and automated Active Response fired accurately.
* Document findings and close as **Authorized Activity**.

### Confirmed Malicious / Malformed Handshake Flood

* Confirm sustained abnormal 3-way handshake corruption targeting endpoint services.
* Validate that automated Active Response dropped the IP, or escalate if packets continue to bypass.
* Close as **True Positive — Denial of Service Attempt / Handshake Corruption Flood**.

### False Positive / Severe Network Retransmission Corruptions

* Check for hardware-level packet corruption or badly misconfigured TCP middleboxes/optimizers mangling packet headers in transit.
* Adjust rule thresholds if legitimate network equipment repeatedly breaches the 10-event threshold.

---

## 6. Automated Containment Verification

* Check Wazuh Manager active response logs:
* Look for `active-response/bin/firewall-drop` execution against `<SRC_IP>`.


* Verify endpoint firewall state:
* Run `sudo ufw status numbered` or `sudo iptables -L -n -v` to ensure the drop rule is actively matching.


* Confirm TCP state table clearance:
* Verify half-open connections have cleared and listener backlog is healthy (`ss -tan state syn-recv`).



---

## 7. Documentation & Review

* Log incident details, attack timeline, total suppressed volume, and impact metrics.
* Review if the 30-second cooldown (`ignore="30"`) adequately protected the SIEM queue during the attack window.

# Runbook — Multiple Suricata Stream Established SYN Resends with Conflicting Sequence Numbers

## 1. Metadata & Overview

**Purpose:** Investigate high-frequency TCP stream anomalies where unexpected `SYN` packets with conflicting sequence numbers are injected into active, already-established connections from a single source IP.

**Scenario:** In-session TCP desynchronization, blind TCP connection reset/hijacking attempts, or stateless flood tools hammering established sockets to force teardowns.

**Environment:** SOC Lab / Ubuntu Endpoint / Suricata NIDS / Wazuh SIEM

---

## 2. Trigger & Alert Information

**Wazuh Rule:** `100027`

**Level:** `8`

**Description:** Multiple SURICATA STREAM ESTABLISHED SYN resend with different seq from SAME IP.

**Parent Rule:** `100025` (Base Level 1 rule matching Suricata SID `2210027`)

**Detection Pattern:** 10 or more `2210027` events from the same `src_ip` within 10 seconds (`ignore="30"` active).

**MITRE ATT&CK:** `T1498.001 — Direct Network Flood` (and `T1498 — Network Denial of Service`)

**Tactic:** `Impact`

**Groups:** `suricata`, `soc_lab_scan`, `dos`

---

## 3. Collect Information

Record the following from the Wazuh alert and raw telemetry:

* Alert Timestamp & Incident ID
* Attacker Source IP (`data.src_ip`)
* Attacker Source Port (`data.src_port`)
* Target Destination IP (`data.dest_ip`)
* Target Destination Port (`data.dest_port`)
* Protocol (`TCP`) & Header Flags (`SYN`)
* Agent Name / ID (`agent.name`, `agent.id`)
* Active Response execution logs (`firewall-drop` on endpoint)
* Target socket health (`ss -tan state established`)

---

## 4. Investigate

Check:

1. **Protocol Violation & Sequence Integrity:** In standard RFC 793 operation, `SYN` packets are never sent inside an already established connection. Are incoming `SYN` packets randomized to force kernel `RST` responses or desynchronize sliding windows?
2. **Impact on Legitimate Sessions:** Did existing long-lived sessions (e.g., SSH, database connections, active HTTP streams) drop abruptly or reset during the alert timeframe?
3. **Target Impact:** Did destination listening services drop connections, experience thread starvation, or crash during the packet burst?
4. **Correlated Security Events:**
* Did the source IP trigger concurrent UFW block rules (`100010`, `100011`)?
* Did Suricata trigger related stream rules (e.g., `2210008`, `2210023`, `2210045`) or SYN flood detection (`1000002` / `86601`)?


5. **Source Classification:** Is the source IP a known internal penetration testing node (e.g., Kali Linux lab VM) running flood scripts, or an unauthorized external IP?
6. **Automated Containment Validation:** Verify whether Wazuh Active Response successfully executed `firewall-drop` on the endpoint for the offending source IP.

---

## 5. Decide

### Authorized Testing / Simulation

* Confirm the scan/flood was initiated by an authorized analyst or scheduled lab simulation.
* Verify detection rules and automated Active Response fired accurately.
* Document findings and close as **Authorized Activity**.

### Confirmed Malicious / In-Session Hijack Attempt

* Confirm sustained abnormal stream manipulation targeting active endpoint services.
* Validate that automated Active Response dropped the IP, or escalate if packets continue to bypass.
* Close as **True Positive — Denial of Service Attempt / In-Session Desynchronization**.

### False Positive / NAT or State Table Clears

* Check if an upstream NAT gateway/firewall silently dropped connection tracking states while the client attempted to re-initiate traffic without a standard `FIN`/`RST` teardown.
* Adjust rule thresholds if network middleboxes routinely cause state tracking desynchronization.

---

## 6. Automated Containment Verification

* Check Wazuh Manager active response logs:
* Look for `active-response/bin/firewall-drop` execution against `<SRC_IP>`.


* Verify endpoint firewall state:
* Run `sudo ufw status numbered` or `sudo iptables -L -n -v` to ensure the drop rule is actively matching.


* Confirm TCP state table clearance:
* Verify stale sockets have dropped and listener backlog is healthy (`ss -tan state established`).



---

## 7. Documentation & Review

* Log incident details, attack timeline, total suppressed volume, and impact metrics.
* Review if the 30-second cooldown (`ignore="30"`) adequately shielded the SIEM from queue congestion during the attack window.

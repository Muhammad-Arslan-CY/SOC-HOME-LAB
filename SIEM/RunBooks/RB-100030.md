# Runbook — Multiple Suricata Stream Packets with Invalid ACK from Same Source

## 1. Metadata & Overview

**Purpose:** Investigate high-frequency TCP stream anomalies where received packets contain acknowledgment numbers outside the valid TCP sliding window or on sockets where the ACK flag is illegal in the current state.

**Scenario:** TCP ACK flood, stateless packet crafting/fuzzing, sequence manipulation attacks, or state table exhaustion attempts targeting endpoint network interfaces.

**Environment:** SOC Lab / Ubuntu Endpoint / Suricata NIDS / Wazuh SIEM

---

## 2. Trigger & Alert Information

**Wazuh Rule:** `100030`

**Level:** `8`

**Description:** Multiple SURICATA STREAM Packet with invalid ack from SAME IP.

**Parent Rule:** `100028` (Base Level 1 rule matching Suricata SID `2210045`)

**Detection Pattern:** 10 or more `2210045` events from the same `src_ip` within 10 seconds (`ignore="30"` active).

**MITRE ATT&CK:** `T1498.001 — Direct Network Flood` (and `T1498 — Network Denial of Service`)

**Tactic:** `Impact`

**Groups:** `suricata`, `soc_lab_scan`, `dos`

---

## 3. Collect Information

Record the following from the Wazuh alert and raw telemetry:

* Alert Timestamp & Incident ID
* Attacker Source IP (`data.src_ip`)
* Attacker Source Port (`data.src_port`)
* Target Destination IP (`data.dest_ip`)
* Target Destination Port (`data.dest_port`)
* Protocol (`TCP`) & Header Flags (`ACK` / crafted flag combinations)
* Agent Name / ID (`agent.name`, `agent.id`)
* Active Response execution logs (`firewall-drop` on endpoint)
* Target system state (CPU load, network interface drop counters, socket state)

---

## 4. Investigate

Check:

1. **Protocol Violation & Window Validation:** Are the acknowledgment numbers mathematically outside the established TCP sliding window, or are `ACK` packets arriving for non-existent connections (classic signature of `hping3 --flood -A` or raw socket injectors)?
2. **Traffic Pattern & Scope:** Is the traffic directed at a single active listening port (attempting service state exhaustion) or scattered across random unassigned ports (blind probing/fuzzing)?
3. **Target Impact:** Did the endpoint kernel experience elevated CPU usage generating `RST` packets, or did legitimate network throughput degrade during the burst?
4. **Correlated Security Events:**
* Did the source IP trigger concurrent UFW block rules (`100010`, `100011`)?
* Did Suricata trigger related stream rules (e.g., `2210029`, `2210023`, `2210008`) or custom DoS rules (`1000002` / `86601`)?


5. **Source Classification:** Is the source IP a known internal penetration testing node (e.g., Kali Linux lab VM) conducting flood simulations, or an unauthorized external address?
6. **Automated Containment Validation:** Verify whether Wazuh Active Response successfully executed `firewall-drop` on the endpoint for the offending source IP.

---

## 5. Decide

### Authorized Testing / Simulation

* Confirm the ACK flood or scan simulation was initiated by an authorized analyst or scheduled lab exercise.
* Verify detection rules and automated Active Response fired accurately.
* Document findings and close as **Authorized Activity**.

### Confirmed Malicious / Hostile ACK Flood

* Confirm sustained transmission of out-of-window/invalid ACK packets targeting endpoint resources.
* Validate that automated Active Response dropped the IP, or escalate if traffic continues to bypass.
* Close as **True Positive — Denial of Service Attempt / Stateless ACK Flood**.

### False Positive / Asymmetric Network Routing

* Check for asymmetrical routing paths where outbound `SYN` or `DATA` packets traverse a different gateway than incoming `ACK` replies, causing Suricata's stream tracker to lose window synchronization.
* Adjust rule thresholds if legitimate multi-path network routing consistently triggers the 10-event window.

---

## 6. Automated Containment Verification

* Check Wazuh Manager active response logs:
* Look for `active-response/bin/firewall-drop` execution against `<SRC_IP>`.


* Verify endpoint firewall state:
* Run `sudo ufw status numbered` or `sudo iptables -L -n -v` to ensure the drop rule is actively matching.


* Confirm TCP state table clearance:
* Verify sockets have normalized and interface error counters are clear (`ip -s link show enp0s8`).



---

## 7. Documentation & Review

* Log incident details, attack timeline, total suppressed volume, and impact metrics.
* Review if the 30-second cooldown (`ignore="30"`) adequately shielded the SIEM from queue congestion during the attack window.

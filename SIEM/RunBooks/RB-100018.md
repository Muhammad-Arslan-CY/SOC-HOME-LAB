# Runbook — Multiple Suricata Stream Established SYN-ACK Resends with Divergent ACK

## 1. Metadata & Overview

**Purpose:** Investigate high-frequency TCP stream anomalies where retransmitted SYN-ACK packets carry conflicting acknowledgment numbers from a single source IP.

**Scenario:** Stateless TCP fuzzing, sequence desynchronization attacks, or raw packet crafting (`hping3`, `scapy`) attempting session hijacking or state table exhaustion.

**Environment:** SOC Lab / Ubuntu Endpoint / Suricata NIDS / Wazuh SIEM

---

## 2. Trigger & Alert Information

**Wazuh Rule:** `100018`

**Level:** `8`

**Description:** Multiple SURICATA STREAM ESTABLISHED SYNACK resend with different ACK from SAME IP.

**Parent Rule:** `100016` (Base Level 1 rule matching Suricata SID `2210023`)

**Detection Pattern:** 10 or more `2210023` events from the same `src_ip` within 10 seconds (`ignore="30"` active).

**MITRE ATT&CK:** `T1498.001 — Direct Network Flood` (and `T1498 — Network Denial of Service`)

**Tactic:** `Impact`

**Groups:** `suricata`, `soc_lab_scan`, `dos`

---

## 3. Collect Information

Record the following from the Wazuh alert and raw telemetry:

* Alert Timestamp & Incident ID
* Attacker Source IP (`data.src_ip`)
* Attacker Source Port (`data.src_port`)
* Target Destination IP (`data.dest_ip`)
* Target Destination Port (`data.dest_port`)
* Protocol (`TCP`) & Header Flags (`SYN-ACK`)
* Agent Name / ID (`agent.name`, `agent.id`)
* Active Response execution logs (`firewall-drop` on endpoint)
* Target system state (CPU load, socket exhaustion, packet loss metrics)

---

## 4. Investigate

Check:

1. **Protocol Violation & Packet Integrity:** Standard RFC 793 stacks never alter acknowledgment numbers across retransmissions of the same SYN-ACK segment. Are ACK numbers arbitrary or incrementing abnormally?
2. **Traffic Pattern:** Is the attack targeting an existing open port (e.g., port 80/443/22) or probing closed ports across the host?
3. **Target Impact:** Did destination listening services drop connections or experience thread locking during the packet burst?
4. **Correlated Security Events:**
* Did the source IP trigger concurrent UFW block rules (`100010`, `100011`)?
* Did Suricata trigger related stream rules (e.g., `2210022`, `2210008`, `2210027`) or SYN flood detection (`1000002` / `86601`)?


5. **Source Classification:** Is the source IP a known internal penetration testing/simulation machine (e.g., Kali Linux lab VM) or an unauthorized external actor?
6. **Automated Containment Validation:** Verify whether Wazuh Active Response successfully executed `firewall-drop` for the offending source IP.

---

## 5. Decide

### Authorized Testing / Simulation

* Confirm the scan/flood was initiated by an authorized analyst or scheduled lab simulation.
* Verify detection rules and automated Active Response behaved as expected.
* Document findings and close as **Authorized Activity**.

### Confirmed Malicious / Hostile Flood

* Confirm sustained abnormal stream manipulation targeting production services.
* Validate that automated Active Response dropped the IP, or escalate if traffic bypasses controls.
* Close as **True Positive — Denial of Service Attempt / Stateless Packet Injection**.

### False Positive / Network Asymmetry

* Check for middlebox proxy retransmissions, asymmetric multi-path routing, or aggressive WAN optimization engines.
* Adjust rule thresholds if legitimate multi-path network devices regularly breach the 10-event threshold.

---

## 6. Automated Containment Verification

* Check Wazuh Manager active response logs:
* Look for `active-response/bin/firewall-drop` execution against `<SRC_IP>`.


* Verify endpoint firewall state:
* Run `sudo ufw status numbered` or `sudo iptables -L -n -v` to ensure the drop rule is actively matching.


* Confirm TCP state table clearance:
* Verify stale sockets have dropped and listener backlog is healthy (`ss -tan state syn-recv`).



---

## 7. Documentation & Review

* Log incident details, attack timeline, total suppressed volume, and impact metrics.
* Review if the 30-second cooldown (`ignore="30"`) adequately shielded the SIEM from queue congestion during the peak attack window.

## 1. Wazuh Rule Ecosystem

The day began with a deeper investigation of the Wazuh rule system and its detection architecture.

The objective was to move beyond basic rule syntax and understand how rules interact with:

* Decoders
* Rule groups
* Rule IDs
* Rule levels
* Parent/child relationships
* Event matching

A significant part of the work involved testing rule combinations and XML structures to understand which tags and values are valid in specific contexts.

### Lessons from failed rule development

Several custom rules failed because of:

* Invalid XML structure
* Unsupported tag combinations
* Incorrect tag placement
* Invalid attribute/value combinations
* Incorrect assumptions about how Wazuh correlates events

One custom detection also turned out to duplicate behavior already provided by a built-in Wazuh rule.

This reinforced an important rule-development practice:

> Always inspect the existing Wazuh ruleset before creating a custom detection.

Custom rules should extend or modify detection coverage rather than unnecessarily reproduce existing functionality.

## 2. DoS Behavior Simulation

The next objective was to simulate DoS attack from Kali against Ubuntu and determine whether Wazuh could detect the resulting activity.

### Lab topology

```text
Kali Linux
    |
    | Simulated DoS traffic
    v
Ubuntu Server
    |
    +-- Apache
    +-- System/Application Logs
    |
    v
Wazuh Agent
    |
    v
Wazuh Manager
```

The initial test did not generate the expected Wazuh alert.

Instead of immediately modifying the detection rule, the event pipeline was investigated.

Apache and the Ubuntu environment were configured so that the generated traffic produced observable events that could be collected and analyzed by Wazuh.

After the required telemetry was available, the behavior successfully triggered the expected detection.

## 3. Wazuh Email Alerting

After validating the detection workflow, email notification was configured for high-severity alerts.

The target configuration was:

```xml
<global>
  <jsonout_output>yes</jsonout_output>
  <alerts_log>yes</alerts_log>
  <logall>no</logall>
  <logall_json>no</logall_json>

  <email_notification>yes</email_notification>
  <smtp_server>192.168.56.101</smtp_server>
  <email_from>marslanmushtaq5@gmail.com</email_from>
  <email_to>pakthunders1@gmail.com</email_to>
  <email_maxperhour>50</email_maxperhour>
</global>

<alerts>
  <log_alert_level>3</log_alert_level>
  <email_alert_level>9</email_alert_level>
</alerts>
```

Therefore, alerts with level 9 or higher should be processed for email notification.

## 4. SMTP Architecture

Instead of relying on Wazuh to communicate directly with Gmail, Ubuntu was configured as a local SMTP relay using Postfix.

The final architecture was:

```text
Wazuh Manager
192.168.56.1
      |
      | TCP/25
      v
Ubuntu / Postfix
192.168.56.101
      |
      v
Gmail
      |
      v
Recipient Inbox
```

This introduced an additional component but provided a useful practical SMTP troubleshooting environment.

---

## 5. Network Troubleshooting

The initial SMTP configuration used:

```text
192.168.100.20
```

This was Ubuntu's address on the separate Kali/Ubuntu lab network.

However, the Wazuh Docker environment could communicate with Ubuntu through:

```text
192.168.56.101
```

Testing from Windows and from inside the Wazuh container confirmed TCP/25 connectivity to the `192.168.56.101` interface.

This highlighted the importance of testing connectivity from the actual client environment rather than assuming that a service listening on an interface is reachable from every network.

# 2. Wazuh Agent Enrollment Troubleshooting

After stabilizing the network, I continued working on connecting the Ubuntu Server Wazuh agent to the Wazuh manager running in Docker.

The Ubuntu agent was configured to communicate with the manager at:

`192.168.56.1`

using:

* **Protocol:** TCP
* **Port:** 1514
* **Wazuh version:** 4.14.6

The Ubuntu machine was also running Wazuh Agent 4.14.6.

---

## 3. Initial Investigation

The agent repeatedly attempted to connect to the manager but was unable to establish a working session.

The logs initially showed:

> `Requesting a key from server: 192.168.56.1`

followed by:

> `Duplicate agent name: Ubuntu. Unable to add agent (from manager)`

This indicated that the manager already had an agent registered with the name `Ubuntu`.

I investigated the local authentication key and confirmed that the Ubuntu system had a `client.keys` file containing an existing agent entry.

The key format was verified to contain:

* Agent ID
* Agent name
* IP setting
* 64-character authentication key

---

## 4. Manager-Side Investigation

The Wazuh manager was inspected from the Docker environment.

The manager initially contained:

* **Agent ID:** 002
* **Name:** Ubuntu
* **IP:** any

The existing agent was removed from the manager in an attempt to cleanly re-enroll the Ubuntu machine.

After removal, the manager was checked again and confirmed that the old agent was no longer present.

---

## 5. Fresh Agent Enrollment

The Ubuntu agent subsequently requested a new authentication key from the manager.

This time, the log showed:

> `Valid key received`

This was an important indication that communication with the manager and the authentication service was functioning.

A new agent entry was created on the manager:

* **Agent ID:** 003
* **Name:** Ubuntu
* **IP:** any

The new key was exported from the manager and installed on the Ubuntu agent.

The local `client.keys` file was verified afterward.

The key was confirmed to have the expected structure and a **64-character authentication key**.

---

## 6. Current State

Despite successfully receiving the new key, the agent continued attempting enrollment and the manager continued returning:

> `Duplicate agent name: Ubuntu. Unable to add agent (from manager)`

The manager currently recognizes:

* **Agent ID:** 003
* **Name:** Ubuntu
* **Status:** Never connected

The Ubuntu agent has the corresponding authentication information locally, but a fully established agent connection has not yet been achieved.

### Important Observation

The problem is no longer simply:

> "The agent cannot reach the manager."

Communication is clearly occurring because:

* The Ubuntu agent can contact the manager.
* The manager responds to enrollment requests.
* The agent has successfully received a valid key.
* The manager is creating/maintaining the `Ubuntu` agent entry.

The remaining issue appears to be related to the agent's enrollment/identity state rather than basic network connectivity.

# 7. What I Learned Today

Today's work provided practical experience with several important concepts:

### Network Infrastructure

* Using pfSense as the central networking component of a virtual security lab.
* Designing a more stable network before performing security monitoring.
* Understanding that SIEM communication depends heavily on correct network configuration.

### Wazuh Architecture

* Wazuh agents communicate with the Wazuh manager over specific ports and protocols.
* Agent authentication relies on an authentication key.
* The manager maintains registered agent identities.
* Agent IDs and names are managed centrally by the Wazuh manager.
* `client.keys` stores the authentication information used by the agent.

### Troubleshooting

I practiced troubleshooting from both sides of the connection:

**Ubuntu agent side**

* `ossec.conf`
* `client.keys`
* `ossec.log`
* `wazuh-agentd`
* systemd service status
* running processes
* agent runtime files

**Wazuh manager side**

* Docker container inspection
* `manage_agents`
* `agent_control`
* manager configuration
* agent registration
* authentication/enrollment behavior

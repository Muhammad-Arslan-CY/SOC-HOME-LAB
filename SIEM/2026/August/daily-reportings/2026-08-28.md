## 2. Technical Engineering & Breakthroughs

### A. Architectural Shift: SIEM-Side State Tracking

* **The Problem:** Suppressing decoder anomalies in Suricata's `threshold.config` dropped raw telemetry before ingestion, causing loss of audit granularity. Conversely, ingesting raw `eve.json` directly generated 2,000–5,000 alerts per flood attack.
* **The Implementation:** Re-architected custom Wazuh detection rules to ingest all Suricata decoder stream events while setting atomic child rules to silent in-memory tracking (`level="1"`). Built multi-tiered frequency aggregations to capture abnormal volume bursts:
* **Base Rule (`level="1"`):** Silently tracks the specific Suricata SID in state memory without writing dashboard alerts.
* **Volume Rule (`level="5"`):** Aggregates 10+ matching events in a 10s timeframe (`ignore="30"`).
* **Correlation Rule (`level="8"`):** Correlates 10+ events from the same source IP (`<same_field>src_ip</same_field>`) for high-confidence identification.



### B. Core Debugging & Resolution

1. **Rule Engine In-Memory Purging (`level="0"` vs `level="1"`):**
* *Issue:* Initial rules set to `level="0"` resulted in 0 alerts during attack simulations.
* *Root Cause:* Wazuh `analysisd` discards `level="0"` events immediately upon decoding, preventing `<if_matched_sid>` child rules from tracking frequency.
* *Fix:* Upgraded base rules to `level="1"`, keeping them active in memory for threshold correlation while staying below the default dashboard alerting threshold (`level="3"`).


2. **Schema & Dependency Corrections:**
* Resolved copy-paste parent ID mismatches (e.g., rules pointing to incorrect base IDs).
* Fixed duplicate rule ID collisions across signatures (`2210045`, `2210029`, `2210024`).
* Expanded the frequency evaluation window from `2s` to `10s` to account for agent-to-manager network latency and batch log processing.

# Day 3 — Wazuh: Custom Detection Rules

Today I moved from simply using Wazuh to understanding how its detection rules actually work.

I started by studying Wazuh rule syntax and the logic behind rule correlation, including:

* `if_sid`
* `if_matched_sid`
* `if_matched_group`
* `same_srcip`
* `same_dstip`
* `same_field`
* `frequency`
* `timeframe`
* Rule levels and IDs

After understanding the basics, I decided to build a custom detection for an SSH brute-force scenario:

Multiple failed SSH authentication attempts from the same source IP, followed shortly by a successful login.

The initial rule went through several iterations. I encountered configuration errors.

Also got my whole wazuh manager crashed for once due to a minor logical error.

I also tested the detection using `wazuh-logtest` and real SSH authentication logs from my Ubuntu VM. This helped me understand an important distinction between:

* Individual authentication failure events
* Correlated authentication failures
* A successful authentication following previous failures

After getting the custom detection working, I investigated why Wazuh was still generating a different Level 12 alert.

That led me to discover that Wazuh already includes a built-in rule, `40112`, specifically designed to detect multiple authentication failures followed by a successful authentication from the same source IP.

This was an important part of today's work.

The goal was not simply to create another rule, but to understand the detection logic well enough to recognize when a custom rule is actually necessary and when existing built-in detection already covers the scenario.


Today's takeaway:

Before writing a custom detection, understand the existing detection rules and correlation logic first. Custom rules should extend detection coverage where necessary, not duplicate functionality that Wazuh already provides.
